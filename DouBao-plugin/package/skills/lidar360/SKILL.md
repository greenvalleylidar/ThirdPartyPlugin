#### Ambiguity Resolution Rules

> When the user's phrasing may match multiple modules, resolve using the following rules:

| User Phrasing | Resolution Rule |
|---------------|-----------------|
| "clip" | Determine by data type: point cloud → `pointcloud_processing`; raster/TIF/imagery → `raster_data_processing`; vector/shp → `vector_data_processing`; if uncertain, ask the user |
| "classify" | point cloud classification (ground/buildings/vegetation/noise/roads, etc.) → `pointcloud_classification`; imagery feature classification (extract semantic features from imagery) → `imagery_processing`; spectral angle classification → `spectral_analysis` |
| "merge" | point cloud merge → `pointcloud_processing`; raster mosaic → `raster_data_processing`; vector merge → `vector_data_processing`; model merge → `model_data_processing` |
| "segment" | individual tree segmentation → `forestry_airborne` / `forestry_terrestrial`; point cloud clustering segmentation → `pointcloud_processing` (`segment_by_attribute`) |
| "extract" | extract point cloud by attribute/elevation/echo, etc. → `pointcloud_processing`; extract raster value to point → `vector_data_processing`; extract building footprint → `building_modeling`; extract roads → `pointcloud_classification`; extract trunk → `forestry_terrestrial` |
| "orthophoto/DOM" | generate from imagery project → `imagery_processing` (`orthomosaic`); generate from aerial triangulation result → `terrain_analysis` (`generate_dom_by_pixel_mode`) |
| "directory tree/current directory" | Route `platform` only when the context explicitly points to LiDAR360, project, layer, data management panel or `.liaep` image project; if there is a disk path, folder, workspace, repository or Shell context, it will be processed according to the meaning of the file system; if the context is insufficient, do not scan the disk to infer the LiDAR360 status |

#### Unmatched Fallback Rule

> When a user request does not match any of the above keywords, **do not guess the route**; you must ask the user for more information:

**Follow-up Strategy:**

1. **Ask about data type** (if data processing is involved):
   - "What type of data do you want to process? (point cloud / raster imagery / vector / model / other)"

2. **Ask about the specific operation goal** (if the user description is vague):
   - "What specific functionality do you want to achieve? For example: clip, classify, convert format, generate DEM, extract features, etc."

3. **Ask about the data source** (if it involves multi-module functionality):
   - "Is your data airborne LiDAR data or terrestrial LiDAR data?"
   - "Do you want to generate the orthophoto from an imagery project, or from the aerial triangulation result?"

4. **Ask about the processing stage** (if it is a complex workflow):
   - "What processing stage are you currently at? For example: data import, preprocessing, classification, analysis, export, etc."

**Example Follow-up Scenarios:**

| User Request | Follow-up Content |
|--------------|-------------------|
| "Help me process this file" | "What type of file do you want to process? (point cloud / raster / vector / model) What functionality do you want to achieve?" |
| "Help me analyze it" | "What data do you want to analyze? What do you want to analyze? (terrain / forest / spectral / change detection, etc.)" |
| "Help me convert it" | "What format do you want to convert from and to? (LAS→LiData, TIF→IMG, point cloud→3DTiles, etc.)" |
| "Help me extract information" | "From what data do you want to extract what information? (extract boundary from point cloud / extract buildings from imagery / extract contours from DEM, etc.)" |

**Important Principles:**
- It is better to ask one more question than to route incorrectly
- After follow-up, re-match the routing rules based on the user's reply
- If still undetermined after follow-up, suggest the user refer to the module index table to choose manually

## Usage Conventions

- **Tool invocation**: must first detect the enabled LiDAR360 service via `mcp_tool.exe detect_mcp` before invoking tools, with the convention `{module_name}-toolID`, parallel invocation is prohibited
- **General conventions**: parameter query, pre-execution checks, output path generation and error handling refer to `references/profiles/tool_call_conventions.md`
- **Command-line tool**: `mcp-tool.exe` usage details in `references/profiles/mcp_tool_usage.md`
- **Workflows**: cross-module workflow index in `references/workflow/workflow.md`, UAV full workflow in `references/workflow/uav.md`

### Common Workflows

| Workflow | Module Chain |
|----------|--------------|
| Standard point cloud processing | platform → data_preprocessing → pointcloud_processing → pointcloud_classification → terrain_analysis → data_conversion |
| Imagery and point cloud fusion | platform → imagery_processing → terrain_analysis → pointcloud_processing → data_conversion |
| Forestry survey | platform → pointcloud_processing → pointcloud_classification → terrain_analysis → forestry_airborne/forestry_terrestrial → data_conversion |
| Building modeling | platform → pointcloud_classification → building_modeling → imagery_processing → model_data_processing → data_conversion |
| Remote sensing raster analysis | platform → raster_data_processing → spectral_analysis → vector_data_processing → data_conversion |
| UAV | platform → data_preprocessing → pointcloud_processing → pointcloud_classification → terrain_analysis → imagery_processing → data_conversion |

## Common Pitfalls and Tips

- **Parallel invocation of LiDAR360 tools is prohibited**: multi-step tasks must be executed one by one in sequence, waiting for the previous tool to return before invoking the next.
- **Confirm data type before routing**: when encountering ambiguous operations such as "clip", "classify", "merge", "segment", first determine the module based on point cloud, raster, vector, model or imagery project; if undetermined, you must ask.
- **Classification and attribute writing tools may modify data in place**: before invoking, check the in-place modification tool list in `references/profiles/tool_call_conventions.md`, clearly warn of the irreversible risk, and execute only after user confirmation.
- **Check data compatibility first for multi-input tasks**: operations such as registration, merge, mosaic, change detection should first check whether coordinate system, spatial extent, data format and necessary attributes are consistent.
- **Use the schema `title` to generate output paths**: do not directly use the tool ID as the output file extension; also check for illegal characters, extensions and Windows path length limits.
- **Do not guess parameters from natural language alone**: before each tool invocation, you must execute `{SKILL_DIR}/scripts/mcp-tool.exe get_tool_schema "module-toolID"` to obtain the current runtime schema, and based on it confirm required parameters, enum values, value ranges, input counts and return structure. On failure, mark `schema_source: unavailable`, `status: blocked` and stop execution; do not fall back to local `schemas` snapshots, business documents or memory to execute.
- **Verify intermediate results step by step for cross-module workflows**: after each step, check the return code, output path and data validity, and pass the result to the next module only after verification passes.
- **Do not blindly retry on errors**: first check the error message as well as input path, output path, parameter type, file count, format, coordinate system and spatial extent, then decide whether to correct parameters, switch tools or ask the user.
